What the run needed that the plan did not foresee

  movement_types.movement_type_name that does not list 'balance-reversal', and
  ADD CONSTRAINT validates every existing row. Production already held
  movement_types id 11 and transaction_types id 7, put there by an accidental
  boot that ran ensureBalanceReversal() - the boot counterpart of 037, the last
  file in the chain. Both rows were measured unreferenced (0 usages each) and
  deleted under NOT EXISTS guards, DELETE 1 and DELETE 1, and 037 reinserted
  them at the end of the chain. The migration was not edited: changing its value
  list would desynchronise it from 037 and from populateDB.js, and db:parity
  compares constraint definitions as text.

  036, 037 and 038 were applied in a second command because the first run
  stopped after 035. 036 and 038 open with DROP CONSTRAINT IF EXISTS and 037
  uses a drop loop, ON CONFLICT DO NOTHING, ADD COLUMN IF NOT EXISTS and
  CREATE INDEX IF NOT EXISTS, so all three were re-runnable against the state
  the boot had left.
