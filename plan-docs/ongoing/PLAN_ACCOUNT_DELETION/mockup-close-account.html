FinTrack · account deletion

Close account — the walk and every state

Thirteen frames at the 360px design width: five steps of the sequence and the nine states the screen can be in. The preview is a GET on /delete/close_preview/:targetAccountId, the close a DELETE on /delete/:targetAccountId. Open questions and missing tokens are at the foot of the page.

Screen copy

The toggle changes the screen copy only. These notes and the appendix stay in English: they are documentation, not interface.

The sequence, and what each step carries forward

Step 1 — the screen loads GET /delete/close_preview/:targetAccountId

Carries in: the account id from the route, and the name, type and currency from the list the reader came from. Carries out: targetAccount.residual as text, destinations[] and destinationCount. Frames 01, 06, 07, 08.

Step 2 — the settlement choice and the reason

This is the step the method choice used to be. Carries out: policy, destinationAccountId when the policy is a transfer, the typed closeReason, and expectedResidual — the residual string exactly as received, never the formatted figure. Frames 02, 03, 04, 05.

Step 3 — the confirmation dialog

Read-only. It restates every value from step 2 and adds nothing of its own. Frames 10 and 11.

Step 4 — the call DELETE /delete/:targetAccountId

Body: deletionType: 'CLOSE', policy, destinationAccountId, expectedResidual, closeReason. The dialog is not dismissible. Frame 12.

Step 5 — the outcome

On success the dialog closes and the page becomes the outcome view, reading settledResidual, destinationAccountName and the policy off the response. On a refusal the dialog stays and states what did not happen. Frames 09 and 13.

Decisions the brief did not settle

  1. Frame 02 and frame 06 cannot both be right, and this is the one thing to rule on first. The close operation that ships today in deleteAccountService.js settles any residual by moving it or discarding it and never refuses for a non-zero balance; the close sequence written in PLAN_CLOSE_ACCOUNT.md refuses unless the balance is already zero on bank, cash, investment and debtor, and says in as many words that closing moves no money. Both frames are drawn because both states were asked for. Which rule governs?
  2. The backend refusal text is not rendered as received. The screen owns its copy and keys off the outcome, so both languages read the same sentence. What it costs: the sentence the server actually threw is not shown, and the two can drift. What it needs: today a 403 carries two unrelated causes — a reserved name and a non-creatable type — in prose alone, so the screen cannot tell them apart without a machine-readable code on the error payload. Frame 07 assumes one exists.
  3. The translation helper cannot interpolate. useLanguageTranslation returns translateText(key) and getLangText hands back a raw string, so a sentence naming the account or the amount has no way to receive it. This mockup substitutes {name} and {amount} at render time. The alternative the module uses today — splitting the sentence around a rendered span — produces ungrammatical Spanish, because the word order differs.
  4. The confirmation dialog has no checkbox. Carlos ruled that out. The consequences are listed in the dialog itself, beside the button.
  5. Frame 06 is drawn on an investment account. If the refusal survives the first ruling above, it has to name a type whose balance this screen cannot settle by itself, and an investment position is the clearest case: transfer destinations are bank accounts, so there is no in-screen route.
  6. The closing date is printed 08/09/2026 and nothing decides that format. A date is data, so it takes no dictionary key, but day-first and month-first are different sentences to an English reader and to a Spanish one. Either the screen formats it against the active language or the payload carries a formatted string; neither is settled and this frame simply picks one.
  7. The reason field imposes no maximum length, because the contract states none. If the column lands as a bounded type the field needs a counter and a limit.
  8. The confirm button is off until the reason holds a non-space character, and the field states why. An always-live button would send a request the database constraint is going to refuse.
  9. The destructive button is drawn from the error banner triad rather than from the cream accent every other submit uses, so the one control that deletes an account row does not look like an ordinary save. White on that red computes to 5.89:1, which is arithmetic on the token values and not a measured render.
  10. The refusal for a system account offers a rename button. The backend’s own message says to rename the account if it is the owner’s, so the remedy it names now has somewhere to go.

What the screen sends, and what it must not send

  1. expectedResidual is the residual string exactly as the preview handed it over. The figure on screen is formatted for reading and is never the value that travels back; the settlement compares the echo against a balance it derives under its own lock and refuses if they differ.
  2. closeReason is free text the owner typed, stored verbatim and never translated. Only its label, its hint and its validation message have keys.
  3. Account names and currency codes are data, not keys. They are never looked up in the dictionary. Neither is the reason. Everything else on these frames is.
  4. The account type is the one piece of data that is also a key, because ImpactReportUI.tsx already calls t(affectedAccountType) and the dictionary answers. The values printed here are the shipped ones, so the refusal list reads Income and Expense rather than income source and category budget. Two types have no entry, cash and boundary, and getLangText falls back to the key, so a cash account prints the literal string cash today.
  5. Every row in a list is keyed on its own identifier — a destination on its accountId — never on its position in the array. A closure changes the length of exactly these lists.
  6. Every clickable thing on these frames is a real button or a native control, so it has focus, a visible focus ring and an announced role.

Tokens this screen needed and the file does not have

  1. A placeholder fill for a skeleton. Nothing in tokens.css names one. On the dark surface the skeleton borrows --color-surface-raised and on the cream panel --color-surface-disabled, neither of which means "loading". A pair for the two surfaces is the shape it wants; no name is proposed here and nothing in the CSS invents one.
  2. A destructive action colour and its content colour. There is no button token for an irreversible action. The one used here is composed from --color-feedback-error-content and --color-surface-inverse, which is a banner colour pressed into service as a button ground.
  3. Nothing else was missing. Every other value on this page resolves to a token declared in frontend/src/styles/tokens.css, copied here value for value.

What is deliberately avoided

  1. --radius-lg is not consumed. Three stylesheets in this same lazy route write --radius-lg: 0.5rem into the global :root, so a panel built on it would render at one value here and another in the app. The panels use --radius-md.
  2. Every class is prefixed close-. The generic names in this codebase are declared in several stylesheets at equal specificity and the winner depends on which lazy route loaded last.
  3. The reset at the top of this file reproduces the universal-selector font size from index.css on purpose, so the CSS here has to survive it. Every inline element restates font-size: inherit. That 16px is the only raw pixel value outside the token block and the media query conditions, and it is a verbatim copy.
  4. No prefers-color-scheme block. The one in the codebase is inverted and this screen does not extend it.

What has not been verified

  1. The Spanish has not been read by a native speaker. It was written to match the length of the English so the layout holds in both, which is a layout decision, not a copy review.
  2. The typeface is a fallback. Outfit is fetched by index.css from Google Fonts and this file makes no external request, so line lengths and letterforms here are not the app’s.
  3. The three-across grid above 1024px is the review shell’s, not the app’s. The screen itself is a single centred column at every width.
  4. The focused settlement option draws two rings. The radio carries its own 2px ring and the card around it lights up as well, because .close-option:focus-within repeats it at card size. Both are legible in the screenshots; whether the pair reads as noise is a judgement on a real screen. If it does, the rule to delete is .close-option:focus-within and the radio keeps its own.
  5. The dialogs are drawn inside a 360px frame with a static scrim. Focus trapping, the Escape key and scrim-click dismissal are behaviour, not layout, and none of it is exercised here.
